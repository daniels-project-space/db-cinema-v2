# Admin authentication security

The current public Convex queries and mutations accept a shared administrator token directly. `adminAuth.verify` is public, as are other token-protected queries. Failed authentication attempts are **not** rate-limited or durably logged: Convex rolls back writes in a mutation that throws. Successful mutation audit entries also roll back if the encompassing mutation fails. Do not treat the old failed-attempt counter or log as evidence of protection.

A rate limit on the website login or on `adminAuth.verify` alone would not protect the other public endpoints. A global attempt counter would also let an unauthenticated attacker lock out all administrators. Before enabling sensitive new customer controls, replace direct shared-token access on every public endpoint with individually scoped, revocable administrator sessions and enforce authentication server-side. Put durable, abuse-resistant attempt throttling at a boundary every authentication attempt must traverse, including direct Convex access. Review second-factor authentication, recovery, secret rotation, session expiry, audit integrity and incident response. Avoid assuming a password's entropy from its length.

This document records a finding, not a completed mitigation. No production credentials or settings were changed.

## Internal session foundation (not enabled)

`adminSessionsV2` contains internal-only, expiring and revocable scope records and an independent per-client fixed-window attempt counter. The experimental `adminSessionIssuerV2` is an internal action; `/admin-session` is a hard-disabled HTTP delivery path with no production callers. Neither protects existing endpoints. The delivery path accepts only approved origins, a bearer identity JWT and bounded JSON containing a trusted gateway's signed attestation; it returns the session token without caching. It does not itself verify a JWT from text: it relies on Convex authentication to supply the identity to the issuer. Its integration test mocks identity and readiness, not the provider or network. The standalone counter returns a denial instead of throwing so a caller can commit its result. The issuer requires an identity supplied by Convex authentication, a server-configured identity-to-scope assignment, and a short-lived HMAC-signed client attestation bound to that identity. Its admission mutation atomically checks the per-client window, consumes the attestation nonce on admission, and stores only a digest of a new 256-bit random session token. Rate-limited requests do not create nonce rows; an unexpired denied attestation may be retried after the window resets. The token is returned once; a lost response requires a new attestation and can leave an unused session until expiry.

The issuer is not ready for use: no Convex identity-provider configuration, scope assignment, or cleanup schedule has been set up or verified. A hard-disabled Vercel gateway prototype obtains the admin identity digest from an authenticated Convex query and derives its client digest from `x-vercel-forwarded-for` rather than browser-supplied JSON; tests mock Vercel and identity. Vercel documents that header as its forwarded client IP, but the actual deployment's edge and proxy behavior must be independently verified before trusting it, and the endpoint must not be enabled on an arbitrary host. The gateway requires an exact configured origin and a signing secret shared securely with Convex; none is provisioned here. Signing attacker-provided client identifiers does not establish client identity. The authenticated identity, attestation and scope configuration are trusted boundaries; a compromised gateway key or trusted internal caller can undermine this design. Shared networks can share a limit and distributed clients can evade a per-address limit. This admission counter runs *after* upstream identity authentication and does not limit failed identity-provider logins. Edge abuse controls, identity-provider throttling, monitoring, key rotation, second factor and a recovery route are also needed. Experimental customer checks re-read the current scope assignment so a removed scope is rejected; other session callers must do the same, and session records must still be revoked separately. The issued token is a bearer credential, not proof of possession: it needs secure transport and storage, XSS/CSRF defenses and incident revocation before exposure to a browser.

Before exposing a session, complete and independently verify the identity-provider and gateway trust boundaries, apply second-factor and recovery controls, and ensure upstream credentials are throttled. Session creation and revocation must remain accessible only to trusted, authorized server paths. Schedule bounded cleanup and evaluate database-cardinality and denial-of-service limits. Test expiry, rotation, revocation and concurrent authentication against a real deployment, not just the fixture harness.

`node scripts/test-admin-auth-convex-runtime.cjs` starts an anonymous loopback-only Convex backend in a temporary directory, configures a generated synthetic RSA key and opens the readiness gate only in that temporary copy. It exercises the actual issuer, session-delivery HTTP route, identity-bound scope check, customer-directory authorization, star mutation, synthetic account-credit grant/retry, notification-device control, sign-out and dual-header verification-document HTTP route with signed JWTs and a synthetic stored document; it rejects wrong issuer, audience, signature, expiry, foreign identity, removed scope, invalid session, unapproved origin, replay and revoked session. Three local mutation/revocation races verify that each completed mutation corresponds to its audit and that no subsequent write succeeds after revocation. This verifies HTTP identity propagation on the local backend, not on production. It does not contact Google or validate the live deployment, identity provider, MFA, edge gateway, JWT refresh or concurrent production cutover. The temporary deployment and credentials are discarded after the test.

`createAdminSessionClient` is an unconnected, in-memory browser session lifecycle prototype for the gateway and issuer. It validates the service URL, sends the identity JWT separately from the scoped token, clears local access before revocation, and attempts to revoke a late issuance after cancellation. Its validation adapter must call the gated identity-bound `checkSession` query for an appropriate scope; `refresh` suppresses local access while checking and clears it if the identity or server authorization changes. Callers must run that check at appropriate boundaries, and server-side authorization remains mandatory for every operation. The prototype conservatively signs out when the JWT changes, including normal token rotation; a production identity adapter must support rotation safely. Its identity, validation and revocation adapters must be supplied by the eventual authenticated client; the current admin page still uses the legacy shared passcode and does not call it. A request aborted after the server creates a session may lose the response, leaving a session unknown to the browser until expiry. Real integration must verify logout, expiry and account switching against the live identity provider.

The existing renter Google sign-in obtains a Google ID token, but exchanges it for a separate renter session and does not configure Convex identity or prove administrator MFA. The unconnected `createAdminConvexIdentityAdapter` can accept a supplied JWT in memory and uses an authenticated Convex HTTP client for the gated session check and sign-out; Convex, not the browser's token-shape check, must verify the JWT and admin scope. Its synthetic fixture composes it with the session client and issuer but mocks the identity provider. Google Identity Services is page-global, so adding a second independently initialized Google button can replace the renter button's callback. Do not connect it to the admin page until the identity provider, MFA policy, page-level coordination, credential refresh, dedicated authenticated Convex client and complete legacy endpoint cutover are designed and verified.

`adminGoogleProvider` is an unconnected helper for a possible future Convex custom-JWT provider: it pins Google's issuer, published signing-key URL and RS256, and requires a specific OAuth client ID as audience. Its values follow [Google's discovery document](https://accounts.google.com/.well-known/openid-configuration); Convex requires an audience for shared issuers such as Google, as described in its [custom JWT documentation](https://docs.convex.dev/auth/advanced/custom-jwt). There is intentionally no `convex/auth.config.ts` in this worktree, so the helper does not register a provider. Before use, compare against the actual deployment's existing authentication configuration, use an approved dedicated admin OAuth client, verify issuer/audience and key rotation against real tokens in an isolated development deployment, and establish a separately enforceable MFA policy. Configuring Google alone does not attest MFA or authorize an administrator.

The unconnected `createAdminAuthController` coordinates that adapter and the session client: it clears local credentials before logout or account switching, notifies subscribers, and exposes the identity token only while a validated scoped session exists. A synthetic fixture exercises account switching and cancellation after server issuance. It is not an admin login screen or an authenticated React provider, and does not establish live identity, MFA, or protection for legacy endpoints. A failed remote logout is surfaced and leaves local access closed, but cannot prove that the server session was revoked.

`AdminIdentityProvider` is an unconnected React boundary for a separate admin Convex client. It hides its children until the session is locally current and Convex reports an authenticated identity, remounts the auth boundary on session changes, and hides the children on expiry. Its browser fixture mocks Convex authentication, so it does not establish real provider propagation or replace endpoint authorization. It deliberately returns no token when Convex requests forced refresh, because safe identity-token rotation is not implemented. Do not mount it with the shared renter Convex client or enable it as a partial cutover.

`accountAdmin.setStarred` has an experimental migration path behind `ADMIN_SESSION_STARRED_V2`. An explicit code-level readiness gate currently prevents enabling it, even if the environment flag is set. Once the gate is legitimately removed, this path rejects the legacy shared token and requires both a scoped session and the same Convex identity used to issue it; revocation is checked in the same transaction as the update. The current client supplies the existing token argument, but the app has no authenticated Convex client provider or session-delivery path. Fixture tests do not establish production identity configuration or transaction behavior. Do not remove the gate until all direct token endpoints and the client login have been migrated and tested, and do not treat migrating one endpoint as protecting the remaining legacy endpoints.

The customer-directory read queries also have an experimental identity-bound `customers:read` path behind `ADMIN_SESSION_CUSTOMER_READ_V2`, with the same hard readiness gate. Setting the flag now causes these queries to fail closed rather than fall back to the legacy token. Without the flag they still use the legacy token; the new path does not secure production. Other modules and all other customer mutations require migration, and test fixtures do not prove the identity provider or live deployment.

The experimental `adminAccountSessionV2.signOut` revokes only the session whose digest and authenticated identity match, in the same transaction. It remains behind the hard readiness gate and has no client integration. Scope removal does not prevent that identity from revoking its own session; neither sign-out nor this session mechanism revokes the legacy shared token.

The account membership, Encore, restriction and note mutations have a similarly gated `customers:write` path behind `ADMIN_SESSION_CUSTOMER_WRITE_V2`. With the flag enabled they fail closed while readiness remains false; with the flag absent they continue using the legacy token. This is migration scaffolding only: the billing portal, other customer actions and other public surfaces remain outside this path, and it does not provide browser session delivery.

The account-credit admin queries and mutations, including the admin branch of shared receipt and history queries, have an experimental `payments:read` / `payments:write` path behind `ADMIN_SESSION_CREDIT_V2`. The hard readiness gate prevents its use, and the legacy token remains in use without the flag. Customer-owned credit reads continue to use their existing account sessions. Fixture tests mock readiness to exercise the scoped path; this does not verify a production identity provider or protect other credit-changing flows.

`adminBillingPortal` has a separate experimental `payments:write` path behind `ADMIN_SESSION_BILLING_PORTAL_V2`. It checks the current identity-bound session and account-to-Stripe link before and after portal creation, and refuses to return a URL when the session is revoked during the provider call. A provider-side portal session may still have been created; it cannot be atomically rolled back with a Convex transaction. Membership refresh has a separate staged `ADMIN_SESSION_MEMBERSHIP_REFRESH_V2` path: it checks the session before the Stripe read and again in the transaction that updates membership, together with the billing link and membership snapshot. Invoice inspection and other actions still use legacy authentication and need independent migration and action-race review. These gates must not be enabled as a partial cutover.

Verification archive listing, retry, display-failure, backfill, retention-hold and document authorization also have an experimental `verification:read` / `verification:write` path behind `ADMIN_SESSION_VERIFICATION_V2`. Session authorization and the database mutation share a transaction, but the document HTTP route subsequently reads storage outside that transaction: a revoked session cannot retract bytes already authorized or in flight. In gated mode the route accepts the identity JWT in `Authorization` and the session token in `X-DBC-Admin-Session`, relying on Convex to verify and propagate identity. The isolated local Convex test verifies this propagation with synthetic signed tokens; there is no configured production identity provider or client implementation. The gate remains closed, and other verification endpoints, file paths and provider actions still use legacy authentication. Do not enable this flag as a partial migration.

Chat attachment reserve, publish, download and retention controls have gated customer read/write session paths under `ADMIN_SESSION_ATTACHMENTS_V2`; the attachment scanner itself also remains disabled. The admin attachment HTTP route accepts the same dual-header transport in gated mode, but the client and real identity propagation remain unverified, and authorizing a download cannot revoke bytes already in flight. The gated `ADMIN_SESSION_DIDIT_REVIEW_V2` path checks `verification:write` before the provider read and again in the same transaction as local reconciliation. A fixture simulates revocation during that read; it does not prove real identity propagation or provider-side write safety. Didit changes remain console-only, and this mechanism is not permission to issue provider writes or to enable the incomplete gates.

Admin notification queries and mutations have experimental `settings:read` / `settings:write` checks behind `ADMIN_SESSION_NOTIFICATIONS_V2`; delivery workers retain their existing internal-only paths. Tests mock readiness to exercise scope, identity and revocation, while the actual readiness gate stays closed and the default still uses the shared token. The proposed scope assignment is not yet a complete least-privilege review across notification content or other admin endpoints.

The restricted-identity alert and account-recheck queues have experimental `verification:read` / `verification:write` checks behind `ADMIN_SESSION_IDENTITY_ALERTS_V2`; their scheduled workers remain internal and unchanged. The scope assignment is provisional, fixtures mock readiness, and the legacy shared-token path remains active by default. This does not provide biometric matching or resolve retention requirements.

The internal case and inspection-history controls have experimental identity-bound `rentals:read` / `rentals:write` checks behind `ADMIN_SESSION_RENTAL_CASES_V2`. The readiness gate is closed and the browser does not yet provide the required identity and session, so enabling the flag fails closed. Cross-app return context and other rental endpoints still use legacy authentication. The local synthetic test exercises scope, revocation and mutation auditing with a mocked readiness gate; it does not establish production readiness. Do not enable this partial migration.

Stock-reconciliation review has separate staged `rentals:read` / `rentals:write` checks behind `ADMIN_SESSION_SWAP_STOCK_V2`. The manual recheck revalidates the admin session at its preparation, claim, result and final read boundaries; a revocation while the external read runs prevents that admin request from applying its result. The normal scheduled worker remains internal. The readiness gate is closed and the browser identity flow is not yet qualified; the legacy shared token remains the default. Local synthetic tests do not prove production identity propagation or the complete swap authorization boundary.

Cross-app return-inspection context has an independently gated path under `ADMIN_SESSION_RETURN_CONTEXT_V2` requiring both `rentals:read` and `payments:read`, because its payload includes case history and payment settlement data. The identity-readiness gate is closed and Rental Manager is not yet adapted to supply that identity/session; enabling the flag would stop its existing legacy integration. Fixtures mock readiness; no live cross-app authorization has been verified. Do not enable this partial migration.

Drone-licence admin details, legacy-copy archival and review have staged `verification:read` / `verification:write` checks behind `ADMIN_SESSION_DRONE_V2`. The readiness gate remains closed, and renter upload authorization is unchanged. Verification archive access has a separate gate, so neither flag alone completes the end-to-end migration. The focused session tests are synthetic and mock readiness; real identity propagation and the production client remain unverified. Do not enable this partial migration.

For migration, inventory **every** public Convex query, mutation, action, HTTP route and server proxy that accepts the legacy token. Consider Convex's authenticated identity with a trusted issuer and audience, or a server-only gateway whose verified session is enforced by every data path. Enforce a least-privilege scope on each endpoint server-side, and make the authorization check part of the same transaction as protected mutations. External payment and other action side effects need a separate revocation/race and retry design because an external call cannot be committed atomically with the session check. Cut over and disable the shared-token path only after all callers migrate and negative access tests pass, with an operator recovery and rollback plan that does not silently reopen the legacy bypass. Until then, this foundation is not a security boundary.

`node scripts/test-admin-auth-inventory.cjs` compares a conservative inventory of Convex exports, Next API routes, and statically referenced generated public API names with `scripts/admin-auth-inventory.txt`; it also asserts the readiness gate remains closed. Generate a fresh list with `node scripts/admin-auth-inventory.cjs` and review each addition or removal before updating the baseline. The list includes internal helpers and unrelated exports intentionally; an entry is not evidence that a particular endpoint is public or secure. Static analysis cannot discover all indirect, dynamically constructed, external, HTTP-router, aliased namespace, or provider calls, and a matching snapshot is not proof that all authorization paths are covered. Review those separately and perform end-to-end negative access testing before cutover.

The inventory was refreshed after reviewing the added membership invoice and refund-review endpoints, stock-receipt retry, authenticated chat lookup and internal catalogue and settlement helpers. Membership review uses the billing-session migration flag; stock review has its own staged flag; both retain legacy shared-token access by default. Background job and catalogue exports in this batch are internal, while plain exported helpers are not registered as public Convex functions. The refresh does not qualify these flags or change the incomplete cutover status.

The refund-contact alert export is an internal mutation, not an admin entry point. It validates the refund-to-booking binding and only creates a deduplicated owner notification; it cannot send mail or change settlement. Its inventory entry does not qualify the admin-session cutover.
