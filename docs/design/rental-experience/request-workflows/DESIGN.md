# Rental workflow design targets — 9 October 2026

Daniel explicitly rejected the compact, duplicated text-card interface in PR92. Keep PR92 draft and do not publish that presentation. Preserve the qualified functional changes, but rebuild the presentation around these built-in GPT image renders before release.

- `extension-desktop-mobile-v2.png`: administrator extension workspace and separate renter payment screen. Equipment hero, photographic item cards, current/proposed dates, real calendar strip, three-stage approval/payment workflow, quote/decision column and one primary action area.
- `kit-dates-cancellation-v2.png`: matching overlay drawers for kit proposals, rental date changes and cancellation settlement. Equipment thumbnails, before/after comparisons, real selectable dates and clocks, compact financial summaries and explicit actions.

Generation prompt direction: premium DB Cinema management UI matching the existing Customers & Members reference; all charcoal/near-black surfaces, ivory serif headings, precise sans-serif labels, warm-grey outlines, restrained copper actions, cinematic product photography, readable contrast and carefully composed desktop/mobile layouts. Replace duplicated prose cards with equipment, calendar, timeline and quote components. Keep admin and renter controls distinct. All future related panels must follow these references and the established reference images, rather than merely recolouring the old components.

These are design illustrations, not real rental/payment records. Implementation must use actual authorised catalogue images and saved booking/account records, never baked-in customer examples or amounts. Rendered calendars contain illustrative date/weekday labels; the real calendar must compute these correctly. A Sony FX30 must use its real catalogue photograph rather than a render depicting an FX3 body. Approval/decision reasons remain mandatory where the backend requires them even if the illustration says optional. The 'refunds handled separately' illustration must not invent an automatic refund or delay rule; use the actual cancellation/refund policy. Do not promise live availability until the existing stock check confirms it. Do not present an uncaptured hold release as a cash refund or mark completion before actual provider receipts. A rendered time control does not authorize bypassing the existing exact-time, allocation, payment or account fences.

Avoid duplicate 'Customer requests' and 'Extension requests' cards showing the same information. Retain bounded older-request history as a compact secondary activity/history section. Opening a request must reveal its actual controls and status. Default dark styling remains limited to management/account surfaces; landing, gear selection and checkout styling must remain unaffected. Both checkout gates remain closed.

Qualification required before release: genuine images and real state at every stage; actual handler tests; desktop/mobile browser flows; repeated screenshot comparisons against these renders; no cross-account drafts/media/results; head CI and exact production deployment/aliases. Current native receipts qualify the earlier functionality only, not this new design.

Original PNGs are archived in the DB Cinema R2 bucket; see `r2-receipt.json` for immutable object keys and verified SHA-256 readbacks. Local reference copies are development design inputs, not application runtime assets.
