# Withdrawal waits for an in-flight security authorisation

The prior actual 1e90cca addition action could begin card authorisation, wait for Stripe, and race a successful withdrawal. Withdrawal closed its rental lock before the new hold was bound. When the delayed authorisation finished, its binding could not attach the withdrawn item, but the new card hold remained uncancelled. The previous durable withdrawal decision solved attachment; it did not prove cleanup of this external effect.

The action now commits the exact approved manual-capture authorisation request and preparation timestamp before sending it. Attachment and closure cannot finish while that request is unresolved. Binding its provider result clears the pending marker while preserving withdrawal state. Both normal completion and withdrawal recover the same frozen request/operation identity. A concurrent provider request/conflict retains the operation and physical stock until the result can be recovered and the replacement hold cancelled. Original rental security remains separate.

Recovery uses a conservative 23-hour replay window because [Stripe can prune idempotency keys once they are at least 24 hours old](https://docs.stripe.com/api/idempotent_requests). Within that window it replays the exact already-approved request with the original key; if the first transmission did not arrive, completing that prepared attempt can authorise the agreed hold before immediately cancelling it for withdrawal. After the cutoff it only searches and retrieves provider evidence for the saved attempt, validating amount, currency, manual capture, customer, payment method and booking/addition/purpose metadata. If the outcome cannot be proved, it retains the lock and requests provider reconciliation; it creates no new hold. Frozen card/customer parameters remain in internal context and are excluded from the admin list projection. Native reference consulted with task-local official Stripe CLI v1.53.1; app SDK remains 22.6.2.

Withdrawal checks the cancellation result before closure. Captured or partially captured replacement security requires financial reconciliation and cannot be described as an uncaptured release. Item-addition Checkout creation now follows dynamic-method configuration without a fixed payment_method_types array; explicit card allowlisting is retained on the manual-capture authorisation through allowed_payment_method_types. Existing saved sessions resume by their original identity. Live payment-method configuration and legacy interrupted requests need acceptance before rollout.
