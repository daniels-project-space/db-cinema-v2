# Individual return inspection and damage cases

## Account-bound statement delivery — 10 October 2026 draft

Return-statement PDFs preserve the booking's historical billing contact. That contact is not used to choose the email recipient: the worker resolves the permanently associated account, then resolves it again after fetching the private PDF. A missing or blocked linked account stops delivery and leaves the statement retryable; it never falls back to a historical address that may now belong to someone else. Unlinked legacy bookings retain their own contact. The admin email preview resolves the recipient after generating its draft PDF as well. Repeated delivery attempts use the same statement/recipient delivery key through the shared mail transport.

The actual handler regression covers changed and missing accounts, account/contact changes during PDF fetching, blocked accounts, unchanged historical billing, legacy contacts and stable retry identity. This is controlled database/mail-transport evidence, not a live customer email. Production publication and full reference-screen fidelity remain outstanding.

## Admin recovery of a failed original-payment deposit

The return drawer offers an authenticated admin retry with a required saved reason and stable request identity. It first reconciles current receipts. Only failed allocations may be retried; already-successful parts stay untouched. Each failed receipt must have a provider failure balance transaction bound to that receipt, for the exact GBP amount, with refund_failure type and available funds. Unknown, pending, foreign or unavailable proof blocks the new payout. The original captured payment balance is rechecked before creation.

The ledger preserves every previous refund ID, attempt number and returned-money proof before atomically arming a new attempt. New provider metadata and idempotency keys identify that exact attempt. Lost responses are recovered by original source/attempt history, including beyond idempotency retention; replayed or concurrent authorisations cannot create additional attempts. Old callbacks validate their retained identity then reconcile the current attempt. Earlier returned-money proof is checked again on review/recovery, so later contradictory bank evidence stops settlement for admin review. Provider callbacks never authorise new money. The existing indexed recovery schedule resumes an already-authorised prepared attempt.

This does not convert account credit into a cash refund, change the frozen return deductions, or reroute a payment. Failed repayments with no available, matching returned-money proof still require provider/manual resolution. Original-payment availability and bank receipts are authoritative; there is no promise that an issuer must accept another refund. See https://docs.stripe.com/api/refunds/object and https://docs.stripe.com/api/balance_transactions/object.
