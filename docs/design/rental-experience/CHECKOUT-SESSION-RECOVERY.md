# Recover an exact saved checkout before checking new stock

The previous actual checkout action rejects a retry when its own hold occupies the last available camera. The stock check runs before createPending can recover the saved Stripe session. The full checkout screen also disables payment when its reactive stock query sees that hold.

New attempts now save a SHA-256 receipt of the exact validated submitted checkout alongside the accepted booking. Sorted object keys make equivalent serialization stable; the session token is omitted so token rotation does not alter booking particulars. Customer details, complete item/date/quantity lines, expected amount, security choice, delivery, selected membership and agreement/attempt IDs remain bound. No hash is backfilled from guessed historical input.

The private indexed checkoutAttempt query finds the original acceptance attempt. A changed receipt or closed booking rejects before Stripe retrieval. An exact pending booking with a saved session recovers it before new source checks, repricing, reservations or account-credit writes. Stripe must return the saved session ID, matching booking metadata and an open session with a URL. Provider errors/completed sessions do not create a second payment. An ordinary unbound pending outcome stays pending for reconciliation. Interrupted membership binding checks the same saved booking/checkout IDs and creating/open state. Prepared session parameters must identify that booking and reuse the existing Stripe idempotency key; foreign or closed setup never creates a payment.

After an uncertain result, the actual checkout screen offers an explicit Retry secure checkout action only for the unchanged submitted form and acceptance attempt. Its own stock hold can no longer disable that recovery. Edits remove the recovery action; confirmed unbound stock rejection resets recovery and consent. There is no automatic payment retry. Normal new checkout retains fresh-source and transactional stock checks.
