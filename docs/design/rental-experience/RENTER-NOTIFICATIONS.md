# Renter notification bell and delivery

The account header now opens a separate renter notification panel. It explains phone use and Home Screen installation, captures supported browser installation prompts, and requires installation before opt-in on iPhone/iPad. Worker activation and the application-server key are prepared before the customer taps; `PushManager.subscribe` begins from that tap. Opening the panel does not request permission. The customer can choose team messages and booking updates separately, turn off the current device, recover denied permission, and reconnect a missing browser subscription even when the backend still has an enabled row. Mobile retains an explicitly labelled icon button; Escape closes the panel.

Account-only metadata links `/account.webmanifest`; the manifest starts and scopes the app at `/account`. The separate `/renter-notifications-sw.js` worker has no fetch handler or page/API/document cache and does not replace the admin worker. Notification clicks allow only same-origin account chat destinations, with one valid rental ID or the general-support selector. Shopping/admin windows are not redirected. The account page now handles the general-support deep link as well as rental links.

The backend stores renter devices, notification events and delivery attempts separately from admin data. A valid unblocked, verified account session is required to manage a device. Queries return only that account's enabled state and public key/preferences/error. Active foreign session/device/endpoint bindings cannot be taken over; expired or signed-out bindings can be replaced. Subscribe increments a generation, so prior queued work cannot cross account or endpoint reassignment. Preferences and disable enforce ownership. Sign-out disables the session's device registrations before deleting the session.

Actual owner/system calls to `postRentalMessage` queue generic team-message or booking-update notifications. Renter and bot messages do not trigger unsolicited push responses. Event keys deduplicate queueing. Device preferences apply both when queueing and immediately before claiming. A claim checks the subscription generation, account/session validity, rental ownership, current preferences, age and conversation read watermark. An already-read chat update is skipped. Delivery uses the actual `web-push` transport, generic lock-screen text, exact account chat destination, bounded attempts/backoff, claim fencing and a two-minute recovery cron. HTTP 404/410 disables the matching expired generation; late worker results cannot invalidate a newer subscription. Notifications already accepted by a push service cannot be recalled by a later sign-out; no message, document or settlement contents are included in their payload.

`RENTER_PUSH_PUBLIC_KEY` and `RENTER_PUSH_PRIVATE_KEY` must be a complete matching pair. If neither renter key exists, the existing complete admin VAPID pair is reused with separate worker/subscription records. One configured renter key never silently combines with an admin key. No keys were created, exposed, changed or deployed in this work.

## Evidence and limits

- `scripts/test-renter-notifications.cjs` invokes the real registered query/mutation/action and chat/sign-out handlers against controlled database/transport fixtures: session/account/device/endpoint ownership, dedup, preference suppression, actual chat wiring, read suppression, retries, killed-worker recovery, stale worker results, subscription generations, expired subscriptions, blocked/expired/signed-out sessions, account reassignment and private payloads. It also executes the actual worker in a VM for safe links, generic text and shopping-tab preservation.
- The isolated native browser fixture at `/tmp/dbc-renter-notification-fixture` uses the actual bell/overview/shell and actual protected notification/account handlers. Browser push/permission APIs are deliberately stubbed. It checks no permission request on panel open, explicit opt-in, preference persistence, unsubscribe, missing-subscription reconnect, denied permission, iPhone installation prerequisite, Escape and desktop/mobile overflow. Five states were captured and inspected at 1488×1058 and 390×844 in `/root/dbc-renter-notification-review`: opt-in guidance, enabled preferences, messages disabled, permission denial and iPhone Home Screen guidance. Review corrected duplicate permission guidance and an enabled-state recovery error. These state captures are separate from the original six-screen reference fidelity requirement.
- Default regression suite, final typecheck/Next production build and graph update completed successfully. Logs are `/tmp/dbc-renter-push-tests.log`, `/tmp/dbc-renter-push-final-{types,build}.log`, `/tmp/dbc-renter-push-graph.log`, and `/tmp/dbc-renter-notification-recovery-browser.log`.
- Actual local built HTTP responses for landing, gear, checkout and account are 200; only account contains the new manifest. Manifest and renter worker are served at 200. No public page/global stylesheet was changed.

This proves the local implementation and controlled caller behavior. It does not prove production backend deployment, actual configured VAPID keys, real Apple/Google push acceptance, a physical phone Home Screen install, hosted session linking or customer delivery. Those checks, admin settings, paired rollout, accurate hardware imagery, original reference comparisons and the rest of the active integration objective remain open. No real push/email/payment/deployment writes were performed.
