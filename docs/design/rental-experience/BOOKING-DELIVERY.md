# Rental delivery results belong to one attempt

A booking revision can have more than one delivery worker after a lease expires. Previously an older worker could acknowledge the revision or clear the newer lease, because results carried only the booking/revision. A duplicate failure could also consume another retry. Leased rows could repeatedly occupy the beginning of the due batch and delay unrelated bookings.

Each claim now increments a generation and moves the booking's due time to lease expiry. A result must match the booking revision, current pending status, generation and a still-recorded lease. The first result clears the lease; subsequent or earlier-generation callbacks do not change delivery state. A dead worker remains recoverable after expiry. A new booking revision can immediately schedule its own delivery without an old acknowledgement completing it.

The paired manager HTTP response contains `version: 1`, `bookingId`, `receivedRevision`, `appliedRevision` and `outcome`. Manager upsert generates the receipt after applying the particular booking or recognizing identical state; stale updates report the newer stored revision and are not accepted as current delivery. Explicitly pending-payment records return an unpaid skip rather than an invented paid reservation. Unsupported records get no success receipt. Website delivery rejects generic `{ok:true}`, foreign booking/revision, newer revision and unsupported outcomes.

Deploy the compatible manager first; older website senders tolerate additional receipt fields. New website senders keep delivery pending against an older generic manager response. No live deployment is performed by these source changes. Active old workers lacking a generation cannot acknowledge new state and recover through lease expiry.

Validation exercises actual queue/webhook handlers, including a paused first worker, replacement attempt and late receipt. Actual registered manager HTTP route plus real booking upsert verify applied/repeat/new return/stale outcomes, secret/config validation and invalid physical evidence. Database and network transport are controlled. Prior actual 92a26c2 delivery source reproduces the stale acknowledgement (`/tmp/dbc-booking-receipts-negative.log`). Both full local suites, typechecks and safe Next builds pass; manager owner-boundary checks and both graphs pass. Historical generic acknowledgements still require protected resync during rollout; they are not retroactively attested by this change.

This is asynchronous mirror delivery. It does not provide one shared atomic reservation authority or prove live calendars/notifications/cases/provider execution. Those requirements, plus compatible bindings, private document acceptance and full visual/equipment-render work, remain active.
