# Swap stock receipt recovery

The experimental website projection sends the oldest pending applied swap receipt. A receipt from an older booking revision is sent only when the current physical allocations still match it exactly, including allocation and inventory identities, master item, quantities and windows. Rental Manager converts the claim only when its independently written current booking windows also match, and records the original receipt revision. The conversion and manager booking write occur in one transaction. Its authenticated response acknowledges the immutable claim identity; the website records the acknowledgement with its booking-delivery lease and queues another delivery if needed. Changed, missing or ambiguous occupancy leaves the claim held.

The booking-wide stock fence also checks indexed unresolved `rental_item_swaps` states, not just `activeItemSwapId` and applied receipts. A missing booking marker therefore cannot let a different change proceed while an accepted, unpaid, refunding or review-held swap remains open. Only the swap being revalidated may pass its own fence; a second unresolved swap still blocks it.

This does not yet recover every unresolved receipt. New swap previews and proposals, rescheduling, extensions, additions, replacements, cancellation, handover and return now refuse to proceed when a previous receipt is pending, lacks a delivery state, or has a recorded stock risk, even if a booking's active-operation marker was lost. A bounded five-minute sweep now retries the oldest eligible missing-state receipts automatically when their original execution and exact current allocation still match. It restores the rental fence and waits for Rental Manager's independent acknowledgement; it does not assert conversion. Persistent pagination prevents an ambiguous old receipt from starving later candidates. The admin retry remains available for an explicitly reviewed legacy receipt. Other writers and in-flight operations still need a complete audit, and a previously changed booking cannot prove that its earlier allocation remains occupied. Neither absence from the latest booking nor passage of time is evidence that a claim can be released.

Before enabling swaps, add an authoritative reconciliation path for incompatible pending receipts, including legacy records whose current allocation no longer matches their saved windows. Prevent other booking changes from obscuring unresolved allocation evidence, or retain immutable intermediate booking snapshots and order their application at the manager. Reconcile claims whose latest booking no longer covers their windows using authoritative payment and booking history, not an automatic release. Test out-of-order delivery, lost responses, repeated swaps, changed occupancy, cancellation and concurrent manager updates across both deployments. Keep all swap authority gates off until all stock writers participate and end-to-end recovery is verified.

The admin-only “Refund extra payment” recovery for a paid change that is awaiting stock review is independent of the new-swap authority gate. It verifies the exact paid Stripe session and payment, requires explicit confirmation and a reason, and uses the existing refund-approval/recovery path. A successful refund queues stock release but keeps the booking and local reservation fenced until Rental Manager acknowledges it. This refund path does not enable new swaps or prove that stock is available.

Cancellation finalization also checks the stock fence and an active swap before releasing reservations. If a cancellation refund has already been sent when a previously unresolved swap is discovered, the cancellation remains incomplete and needs an operator to reconcile both settlement and stock; retrying must not issue a second refund or silently release the claim. An already-finalized cancellation remains idempotent.

New manual rental refunds also check the stock fence before preparation, even if the booking's active-swap marker is missing. An existing refund request remains retrievable by its original request key; this does not reverse an already initiated provider refund or replace reconciliation of an existing refund job.

New manual refund jobs bind the owner, when known, and the notification email at preparation. A changed or missing contact prevents the chat and email notice and raises an admin alert when the payment result is recorded. The deferred email checks the binding again; a later mismatch suppresses delivery and creates a separate idempotent admin alert. Previously created unbound jobs retain their legacy behavior and need separate review. Provider settlement is still recorded if notification is suppressed.

For a terminal equipment-change refund failure, the admin recovery panel can sync the exact Stripe refund receipt. It verifies the refund ID, original payment, amount, currency, rental, and metadata, then records only Stripe's current status. It never creates a replacement refund or resumes the equipment change automatically. If the provider status is still failed, the admin must reconcile that existing refund in Stripe; after Stripe reports it pending or succeeded, the admin can explicitly resume the existing settlement and stock-receipt flow.

A paid upgrade whose Rental Manager stock check is temporarily unavailable now keeps the existing kit and booking fence, records the original Stripe payment, and schedules a retry of that same settlement. Retries reuse the existing payment and stock-operation identities; they do not create another charge. Three unsuccessful checks stop automation and raise one owner alert for review. This reduces transient sync escalations; it does not resolve a persistent or ambiguous cross-system stock conflict.

Compensated-release reviews use bounded backoff even when the stock bridge throws, rather than repeatedly selecting a failed review and starving the queue. Results are bound to the original retry time and attempt count so concurrent or late checks cannot overwrite newer evidence. Exhausted checks remain in manual review with the rental fence intact. This is recovery hygiene only: it does not prove an external release or permit enabling swaps.
