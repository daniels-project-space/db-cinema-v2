# Shared stock writer boundary

The manager's experimental claim coordinator is not the authority for the website yet. The item-swap feature must remain disabled until the website and manager commit all capacity-affecting writes through a common, authenticated authority and reconcile uncertain provider outcomes. `npm run test:customer-safety` includes a source-inventory guard for direct website reservation insertions and checks that the swap gate is hard-disabled. The guard is a change detector, not proof of complete writer coverage or concurrent correctness.

Known website insertion paths include initial checkout and confirmation, booking add-ons, extensions, rescheduling and handover changes, removal, both legacy replacement paths, the proposed swap ledger, and synchronization of manager stock. Reservation patches and deletes, quantity or catalogue changes, cancellations, returns, late custody, synchronization queues, and indirect or dynamic database wrappers must also be audited; the insertion inventory alone does not detect these. Manager bookings, manual calendar changes, imports and other manager writers likewise require review. Hygglo or other external platforms can create bookings outside either application's transaction; a true exclusive guarantee needs a qualified upstream mechanism, not merely periodic synchronization.

Before removing the hard gate, provide real cross-application concurrency and failure-recovery tests covering every writer, canonical component identities and windows, authenticated request binding, idempotency, claim handoff to confirmed occupancy, payment/refund outcomes and safe claim release. Show that the two representations cannot double-count or lose a claim, and prove behavior under stale or conflicting external stock. Until then do not replace the gate test with feature-flag-only coverage.

On 6 November 2026, Stripe test-mode runs exercised the actual downgrade acceptance and refund handlers and an unpaid upgrade Checkout session with synthetic rental data. The provider recorded one partial refund, retries reused their original refund or Checkout session, and the unpaid upgrade did not change the booking. The manager claim responses and application database were simulated; this is evidence about those test-mode paths only, not a completed upgrade payment, real cross-application stock, live webhooks, or production readiness.

Later isolated two-backend tests exercised hosted Stripe test-mode payment, a test-mode downgrade refund, the actual booking-sync exporter and acknowledgement recovery, and a simulated pending refund resumed after manager conversion. The tests use temporary copies with gates overridden, local transport and synthetic customers. They do not establish production readiness, actual external-platform locking, or automatic recovery of every conflicting payment. The manager rechecks observed capacity before execution and settlement, but an independently accepted Hygglo booking can still arrive after either check. Leave the production gate disabled.

Before converting a website stock claim, the experimental manager also rechecks the whole applied booking against observed occupancy, excluding its own mirror and claim. A conflict rolls back the manager projection and preserves the claim; the website records a first-failure admin alert and continues reconciliation. This catches conflicts already imported at that point, but it does not prevent independent external bookings after conversion or automatically settle their financial consequences.

The experimental booking-claim recovery now fences retry accounting against the state, retry time and attempt count read by the dispatcher. Overlapping dispatchers cannot count the same attempt twice or apply a stale failure to a newer phase. This is local retry protection, not a shared-stock authority or a reason to enable the gate.
