# Gaffer voice interruption evidence

On 6 November 2026, a read-only check of the sales-agent ID configured as the website source default returned `turn_eagerness: eager` and `speculative_turn: true`. The public production homepage's JavaScript also contains that agent ID, although its presence alone does not prove which agent an actual call uses. On 8 November, the website-configured production agent was verified and those two turn settings were changed to `normal` and `false`; provider readback confirmed the values and preserved the other configuration. A safe isolated agent with inert tools is still unavailable, so audible behavior after the change remains unverified.

The five most recent completed conversations for that agent contained 82 transcript entries with an `interrupted` field: two agent entries were marked true. This aggregate does not establish whether the caller, background audio or the agent caused either interruption. No conversation IDs, transcripts, audio or caller details were saved. The website's production agent binding still needs separate verification.

A further read-only aggregate of those five conversations found both interrupted agent entries were the last transcript entry in their respective calls; neither was followed by another user or agent entry. This is consistent with an interrupted ending but does not establish why it occurred or explain reports of overlap during a call. The sample is too small to establish an interruption rate or to justify changing provider settings on its own.

A later read-only sample examined up to the most recent 20 listed conversations, yielding 20 completed calls and 75 agent turns with a boolean interruption field. Three turns were marked interrupted; all three were the final transcript turn. This remains incomplete evidence: more conversations exist, transcript flags may not capture audio overlap, and the data do not establish the cause of a customer-reported interruption. No transcript text, audio or caller identifiers were saved.

An additional read-only trace inspection of five completed calls returned 74 `elevenlabs.recv.agent_response` spans and no named interruption events. Their timestamps included 177 overlapping span pairs, all with identical starts. The meaning and granularity of these received-response spans is unverified; this is not evidence of overlapping audible speech. No trace attributes or customer content were retained, and an isolated audio test remains necessary.

The client sends page and basket context through `sendContextualUpdate`, including after user messages. ElevenLabs describes these updates as non-interrupting background information, unlike user-message events that initiate a response. Their presence alone therefore is not evidence that the client is triggering a second spoken reply. Provider event timing and an isolated audio test are still needed to determine the cause. See [client-to-server events](https://elevenlabs.io/docs/eleven-agents/customization/events/client-to-server-events) and [conversation flow](https://elevenlabs.io/docs/eleven-agents/customization/conversation-flow).

The provider's [conversation detail endpoint](https://elevenlabs.io/docs/api-reference/conversations/get) supports read-only conversation inspection. Before changing live settings, verify the actual production binding, test with an isolated call and compare interruption and turn behaviour. Preserve intentional caller interruption, and verify unrelated agent tools and voice settings after any authorised change.

A subsequent read-only provider configuration check confirmed that this agent has active webhook tools, including a callback request tool, as well as browser client tools. A synthetic call to this production agent is therefore not an isolated test and could invoke operational systems. Use a separately configured test agent with inert tools and synthetic audio before drawing conclusions; the provider settings and customer systems were not modified by this check.

On 6 November 2026, a read-only list of the provider account returned two agents and no further pages. Neither agent was named as a test, sandbox, staging or development agent. Names alone do not prove either configuration is safe to use for testing, so no call was started. Provisioning or using an isolated agent still requires confirming inert tools, cost and operational approval.

A separate local browser regression reproduced a call-ending race: after a goodbye, a brief listening event scheduled the hang-up even if speech resumed before the audio tail elapsed. The no-response backstop could also end an already-speaking goodbye. The local client now cancels the pending tail when speech resumes and does not fire the backstop during speech. The regression uses a mocked provider and does not establish the cause of the reported mid-call overlap or validate real audio.

The mocked-provider browser regression also exercises a delayed tool result across two boundaries: it is delivered to a replacement connection within the same call, but is not forwarded into a later, separately initiated call. This checks the client-side generation fence, not ElevenLabs audio mixing or live interruption behavior.

Another mocked-provider browser regression reproduced a disconnected call's pending goodbye timer ending the next call. Terminal disconnect now clears that timer and invalidates the previous call's callbacks; a goodbye during the greeting-override probe also no longer triggers a reconnect. These are client lifecycle fixes, not proof of the cause of reported mid-call overlap.

The local client now records whether the agent was marked as speaking when an `interruption` event arrived. For `agent_response_correction`, it records only the original and corrected response character counts; neither message text nor caller speech is stored. The admin trace can therefore distinguish caller interruptions during speech from a correction/truncation and inspect their order without keeping additional transcript content. This instrumentation is still local and has not been verified against a production or isolated test call.

ElevenLabs documents `agent_response_correction` as the corrected/truncated response after an interruption, while `interruption` notifies the client that the current response was interrupted. Its conversation-flow guide describes interruption settings as governing whether callers may interrupt, and turn eagerness as controlling when the agent takes a turn. These provider settings can affect turn behavior but do not by themselves prove why a particular call sounded self-interrupted. See [client events](https://elevenlabs.io/docs/eleven-agents/customization/events/client-events), [conversation flow](https://elevenlabs.io/docs/eleven-agents/customization/conversation-flow), and [agent retrieval](https://elevenlabs.io/docs/api-reference/agents/get).

The local provider updater now also proposes `turn_eagerness: normal` and `speculative_turn: false`, alongside the existing concise-response prompt. Its default remains read-only; the apply path verifies the prompt, both turn fields, and preservation of attached tools before reporting success. A focused mock-provider regression passed. At that point, no settings had been applied to the live agent; a real isolated audio call is still required to confirm whether eager speculative turns caused the reported overlap.

On 8 November 2026, a read-only request to the production agent configured by the website confirmed `turn_eagerness: eager` and `speculative_turn: true`. The tested updater then changed only those two fields to `normal` and `false`. Provider readback confirmed the requested values; a canonical comparison of the complete `conversation_config` outside `turn` was identical before and after. The configured agent is named “Db Cinema Rentals - Gaffer” and has active booking tools, so no synthetic call was placed through it. No isolated test agent is identified or verified. Real post-change audio behavior therefore remains unverified.

On 8 November 2026, a local browser regression exposed three separate queued page/basket snapshots being sent together on the first caller turn. The client now keeps the latest state snapshot, preserves only bounded tool-result events, and sends them as one contextual update. The browser lifecycle, caller-turn batching, telemetry, voice-prompt and TypeScript checks pass. This removes redundant context changes from the client path; it does not replace the still-needed isolated provider/audio verification.

On 9 November 2026, a further source audit confirmed that the client distinguishes provider `interruption` and `agent_response_correction` events, queues contextual updates until speech and tool activity have settled, and does not create a second response by injecting a user message. The focused call-race, telemetry, turn-settings and prompt tests pass. No code-level cause for audible mid-answer self-interruption was reproduced. Because the live agent still has booking tools and no isolated agent with inert tools is identified, no real call or provider-setting change was made; provider/audio behavior remains unverified.

On 11 November 2026, a local callback-order regression identified a client-side authorization gap: after a provider interruption, `interruptionAwaitingCaller` and a stale `awaitingAgent` flag could authorize a fresh response before a new caller transcript arrived. That let an interruption without a new request reopen the response gate. The client now ties response starts to an unanswered caller turn, or to a completed client-tool result that needs one same-turn continuation. An interruption invalidates the current stream but no longer authorizes a second answer by itself. Synthetic browser coverage confirms an interruption-only replacement is rejected, a genuine next caller turn is accepted, and a completed tool result can still continue. The response-gate, lifecycle, turn-settings and type checks pass locally. This fixes the demonstrated client race; it does not prove or control whether provider audio itself is interrupted. The live ElevenLabs credential is unavailable in this workspace, and no isolated test agent with inert tools has been verified, so production settings and real audio remain unverified.

On 11 November 2026, a read-only Vercel check found the production environment contains an `ELEVENLABS_API_KEY` variable; its value was not decrypted or exposed. Vercel runtime errors returned no clusters for `/api/voice` or `/api/swml/inbound` in the preceding seven days, and a 24-hour runtime-log search for `interrupt` returned no entries. A broader seven-day text search timed out, so it provides no negative evidence. Vercel logs cannot establish whether ElevenLabs interrupted audible speech. No live key was read, no call was started, and no provider configuration was changed.
