# Private verification portrait rollout

The admin-only portrait candidate references an existing verified selfie document. It does not copy the image or write to the public account avatar fields. A dedicated authenticated, no-store endpoint checks that the account still permits this use and that the requested document is still selected both before and after reading and integrity-checking its bytes. An uploaded or Google profile image always takes precedence. This does not revoke bytes already delivered to a browser or change the team's separately authorised access to verification documents.

The feature is fail-closed. Selection requires `PRIVATE_VERIFICATION_PHOTO_ENABLED=true`, a versioned notice and a separate explicit, revocable account choice. A notice alone or account creation time does not enable use. The account security preference is itself separately gated by `PRIVATE_VERIFICATION_PHOTO_NOTICE_ENABLED=true`; it is available to authenticated accounts regardless of how they were created and remains available for withdrawal when the notice gate is disabled. Existing accounts are not automatically enrolled. A gated, non-blocking prompt offers the choice to recently created authenticated accounts without a profile photo; explicit refusal is saved and does not grant consent. Neither gate should be enabled in production until the notice, legal basis and retention policy have been reviewed, and the choice and private delivery have been verified end to end.

The component is mounted in the admin chat header and, when an authenticated availability check enables it, on the visible directory page of at most ten accounts without profile photos. Each portrait still independently checks consent, verification and retention and is rechecked on its private download; mounted selections refresh once per minute. The chat header discards admin identity and portrait props in renter mode. A local synthetic HTTP test exercises the actual portrait route, including withdrawal while bytes are being read; its database and storage are mocked. Before enabling, complete an authenticated browser test against an isolated deployed backend proving private delivery, withdrawal and removal on account switch or photo upload, the 24-hour delay, expiration and case holds, and no exposure to public or renter-facing profile APIs. Measure query and download usage for a populated directory before rollout. The current automated tests use synthetic records; the integration test exercises real authorization, archive metadata and retention decisions, not a live provider.

An additional disposable local Convex backend test exercises the real portrait HTTP route and storage using synthetic records: an invalid admin token is denied, an authorised request receives the exact private bytes, a new account or existing profile photo prevents selection, withdrawal denies a subsequent request, re-consent restores access, archive expiry denies it, and an open case protects it. The same test renders the actual React components with the real Convex client and confirms image loading, account switching and withdrawal. A test-only local proxy supplies the allowed production origin to the portrait endpoint; the browser, backend and data remain isolated. It does not prove production authentication or delivery, real mobile-browser behaviour, live Didit integration, or approve enabling the feature.

The isolated test also checks that a renter session cannot query admin portrait selection and that the owner's account profile contains neither the selfie document ID nor a selfie-derived avatar URL. This covers those two concrete endpoints, not every possible public data path.

The local portrait-selection queries now follow the staged verification-admin session gate: when enabled, they require the identity-bound `verification:read` scope and fail closed while migration readiness is false. The existing legacy-token path remains active by default. The browser and HTTP transport still need an end-to-end identity-session migration test before the gate can be enabled; the staged query test alone is not production authorization.
