# Component replacement: implementation contract

Status: not enabled. Existing basket replacement switches complete listings; it does not replace a component inside a kit. Adding a separate lens leaves the original kit's missing lens in its stock demand and counts both listings in value and delivery weight.

Rental Manager's owner-only listing editor can explicitly preview and review 30 duration-specific extension adjustments for an existing reviewed replacement. The optional daily preview does not save or infer rates until the owner reviews and saves them; individual durations remain editable. A saved physical-allocation snapshot can apply those rates to extension quotes, but the checkout acceptance and snapshot-creation path is not implemented and remains blocked.

The internal quote now stores a typed proposed offer and current agreement document versions, and has an ownership-checked, idempotent offer-acceptance operation that rejects changed offers and stale stock. Acceptance saves a re-resolved proposed physical allocation and checks its current value using the same helper as existing booking exposure. Neither operation is exposed to customers. This acceptance is not the signed rental agreement, the proposed allocation is not yet a booking allocation, and neither is consumed by booking; the full displayed offer, signed agreement and transactionally recalculated total must be bound together before exposing it or enabling checkout.

`shared/componentReplacement.ts` defines and validates a versioned effective allocation from trusted reviewed rules and verified physical value and weight facts. Rental Manager can record reviewed substitutions with its existing authoritative listing mapping. Its authenticated catalogue feed carries the evidence into the website's listing snapshot, where the importer checks it against the source components and clears stale or malformed evidence. The admin-only preview resolves current master mappings, checks snapshot freshness and checks date-specific stock for the effective kit and any additional supplied lines. It cannot establish that an admin supplied the complete basket. The evidence is explicitly unavailable for checkout and no customer-facing offer is enabled. Focused regressions are `node scripts/test-component-replacement-allocation.cjs`, `node scripts/test-component-replacement-evidence.cjs`, `node scripts/test-component-replacement-preview.cjs`, `node scripts/test-component-replacement-consent-gate.cjs` and `node scripts/test-physical-inventory-parity.cjs`.

The reviewed mapping can also describe a missing original component with a separate `declared:` identity, label, quantity and source URL and excerpt. This descriptor is not an inventory unit and adds no original stock, value or weight to the allocation. The source excerpt is owner-entered evidence, not an independently verified provider receipt. The resulting allocation remains an admin-only preview until the remaining lifecycle checks are implemented.

An experimental internal pricing path now resolves one replacement from reviewed server data, checks it against the complete supplied basket and uses its effective value, weight and reviewed size for existing member-discount and delivery calculations. It rejects multiple substitutions and accessory offers; public checkout and booking do not accept a substitution. This is not a persisted or accepted customer quote, and does not prove payment, physical reservations, fulfilment or future booking changes. Fresh stock and catalogue evidence must be rechecked at the authoritative payment/stock claim. Convex API code generation also needs a configured deployment; the internal reference currently uses the supported runtime proxy until generated types can be refreshed.

The internal calculation also returns versioned canonical pricing evidence covering the resolved basket, stock demands, customer/account identifiers, fulfilment, security and calculated amounts. The internal-only quote issuer hashes that evidence, binds it to an authenticated account or a caller-provided guest capability hash, and saves a 15-minute quote; an owner/request retry returns the same record, while a changed or expired quote is rejected. Expired records are purged after at least 24 hours. Guest capabilities must be generated with a cryptographically secure random source and retained across retries by the eventual trusted caller. The record is not available to customers and does not represent acceptance, hold stock, preserve a full price snapshot, or validate those inputs at booking. Acceptance still requires ownership checks, renewed pricing, and transactional source and stock re-resolution; a stored digest alone is not proof that an agreement was displayed or signed.

The internal booking mutation checks a provided quote record's owner, expiry and supplied digest, then re-resolves each listing's catalogue price, the selected kit's effective physical allocation and security value, delivery load and pricing settings, full basket stock, available credit and relevant membership benefits within the booking transaction before rejecting all substitutions. Quote creation performs the same checks against the action's pricing result. No public checkout sends this proof. This preliminary comparison does not recalculate the full pricing digest, lock external postcode results, consume the quote or accept an agreement; security waiver eligibility, those inputs and lifecycle consumers still require authoritative verification before removing the unconditional rejection.

Bookings have a prospective immutable physical-allocation shape. Inventory checks, Manager stock claims and feeds, reconciliation, rescheduling, extension reservation writes, swap stock calculations and exposure calculations use a saved allocation only after matching it against the persisted booking. This preserves the original allocation across catalogue edits and rejects forged or mismatched lines. Nothing currently creates such a snapshot from a customer acceptance; extension pricing, direct swaps of a substituted line, payment/refund and return lifecycle coverage remain incomplete. Existing fixtures exercise individual handlers, not a complete paid customer rental.

## Authority and customer choice

- Rental Manager must supply explicit, reviewed substitutions between physical inventory units, including the units and quantities replaced, compatible replacement, rental price adjustment and reliable weight and replacement-value facts. Do not infer an interchangeable component or a surcharge from title similarity. A candidate is unavailable when its mapping or pricing is absent or stale.
- `convex/cartReplacements.ts` should return the original kit, the specific unavailable component, the proposed substitute, the adjustment and the resulting kit price. It must check the complete proposed basket against current shared stock. Customer acceptance must identify the exact proposal and basket revision; declining leaves the original basket unchanged.
- Add a persisted, versioned server-issued quote containing the original listing identity, component allocation and quantities, selected substitution, price adjustment, value, delivery weight, dates, expiry and catalogue revision. Revalidate against current source data and live stock before payment. The client must never supply authoritative component quantities, pricing, value or weight.
- Include the accepted substitution and price in the rental agreement snapshot and checkout fingerprint. A changed kit, date, price, delivery quote or mapping requires a refreshed quote and renewed acceptance.

## One allocation across the lifecycle

- Extend the booking line schema in `convex/schema.ts` with the accepted immutable allocation and the displayed substitution. Historical lines without this field retain existing behaviour.
- Make `convex/lib/rentalInventory.ts`, the cart availability queries in `convex/availability.ts`, and the hold creation and confirmation paths in `convex/bookings.ts` consume the same validated allocation. The unavailable unit must be removed once and the replacement added once. Stock claims exported to Rental Manager must use those saved physical reservations, never current catalogue decomposition.
- `convex/lib/rentalAllocation.ts`, extensions, equipment swaps, additions and return handling must use the saved allocation for substituted lines. Preserve per-item dates and quantities. A later catalogue edit must not rewrite a signed booking, and the system must not silently revert to the old component on retry.
- Update `convex/lib/rentalPrice.ts`, `convex/lib/rentalExposure.ts` and the replacement-value calculation to charge the accepted kit price plus the configured adjustment while calculating security and exposure from actual effective components only. Do not count the original and replacement lens together. Ensure discounts and credits apply consistently and the invoice and refund allocation reflect the accepted amount.
- Update `convex/delivery.ts` and each delivery-quote entry path to calculate from the effective kit weight and dimensions, with no duplicate replacement weight. A changed quote must be presented before acceptance.
- Keep `convex/rmv2_sync.ts` and Rental Manager's acknowledged physical ledger aligned with the effective allocation, including pending paid verification, cancellation, extension and stock reconciliation. Display the original kit and its substitution together without treating the replacement as a second full-priced rental.
- Update the account, admin, chat, invoice, shared-cart and recovery representations so a renter and the team can see the same accepted kit and price. No entry path may accept a client-crafted allocation or avoid the stock and consent checks.

## Required verification

1. A kit with an unavailable 16–35mm component and an available approved GM substitute offers the exact component and surcharge; acceptance reserves the retained camera and substitute, but not the original lens.
2. Rejection, quote expiry, concurrent stock changes, stale catalogue revisions, repeated submission and a tampered price, unit or quantity cannot create a payment or change the allocation.
3. Multiple kits, quantities, overlapping periods, other basket lines sharing units, partial shortages, insufficient substitute stock and simultaneous checkouts obey physical capacity.
4. Replacement value and delivery size/weight equal the effective physical kit, and the security calculation, charge, discounts, credit, invoice and refund totals agree.
5. Retry and replay preserve one acceptance, one payment and one physical allocation. Paid pending-verification bookings reserve the same allocation in both systems; cancellation and return release it correctly.
6. Catalogue edits after purchase, extension, reschedule, item swap and separate item return preserve or deliberately update the stored allocation without double counting or losing inventory.
7. Run the actual website-to-manager feed and acknowledgement tests for confirmed and paid pending-verification bookings, plus desktop and mobile customer acceptance tests. Validate real provider configuration and representative inventory mappings separately before enabling the feature.
