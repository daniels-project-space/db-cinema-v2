# Restricted identity alerts

An approved Didit decision can produce the application's existing keyed identity token from the provider's approved name and date of birth. When all required verification checks pass, a bounded indexed lookup compares that token to restricted accounts and queues an administrator notification if another account matches. A match is a lead for human review, not proof that two accounts belong to the same person; people can share a name and date of birth. The match does not itself block a customer or change the booking's approval status. The notification does not include the restricted customer's details; an authenticated administrator can retrieve the candidates for the rental.

This does not perform face recognition or compare identity document numbers. It cannot detect matches when Didit does not return the necessary approved fields, when names differ, or if the existing HMAC key changes. It does not automatically add restrictions or send ban emails. Ordinary raw verification archives follow the rental and case schedule: active rentals preserve them, then the files expire 90 days after the latest linked rental or case closes. The local owner-requested change makes archives permanent and admin-only once an account is manually added to the identity-safety blacklist; access restoration does not remove that marker. This raw-document extension is not released: its lawful basis, necessity, proportionality, rights-request handling, and review schedule still need documented approval. The keyed match signal is pseudonymous personal data and needs its own necessity and retention review. Only synthetic tests have run; no real customer records were used to validate matching.

Approved decisions with an attached identity signal persist a bounded matching job in the verification transaction. A separate worker checks the current booking and queues the alert, retrying transient failures up to five times. An admin-only attention list shows failed checks and offers a manual retry; exhausting retries also queues an owner notification. Completed job metadata, which contains no identity token, is deleted 90 days after completion. Pending or attention jobs are not silently deleted before resolution; they still contain account or booking references and require a reviewed retention and resolution policy, not indefinite retention by default. Delivery of a successfully queued push uses the existing notification delivery and retry system. Production monitoring and end-to-end delivery acceptance are still required.

When Didit fully approves a rental but the provider-attested identity signal is absent or cannot be linked, the approval path sends one advisory owner notice describing the missing identity or allocation signal. It does not enqueue a retry job: retrying cannot restore a provider field that was not attached, and would create a second alert after futile retries. A later Didit refresh with a valid linked signal can queue the actual bounded comparison. The notice does not revoke Didit's approval, compare biometric images, or backfill earlier missing checks.

Each later booking that legitimately reuses an approved verification also queues its own check. The worker rechecks the source session, approved components, account and identity key; a revoked or changed source cannot generate a reused-verification match. For linked rentals the permanent account ID, not a stale booking email, determines which account is the renter. These checks remain alerts for human review and do not block the booking.

Restricting an account starts a paged recheck of verified pending, upcoming and active rentals that already have the same signal. Unblocking invalidates the scan. A missing or malformed signal cannot establish a match and is surfaced for admin attention rather than counted as a clear result. Failures retry with a bounded backoff and an admin retry control; the scan does not alter any matched rental. This still cannot detect different names, missing provider fields or biometric/document-number matches.

Restriction timestamps remain locally preserved across unblocking so a rapid unblock and re-restriction cannot accidentally reuse an earlier check or notice. The new identity-safety retention marker is separate from the legacy field. Fixed-clock synthetic regressions cover the rental/case schedule, permanent blacklist hold, and manual match behavior. This is not evidence of live delivery or approval to release the policy change.
