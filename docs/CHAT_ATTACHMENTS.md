# Chat attachments

The renter and admin upload controls now appear only after an authenticated availability action verifies the configured scanner's private `/health` endpoint, matching nonce, harmless EICAR self-test, ClamAV version and signature freshness. A configured URL/token alone is insufficient: `CHAT_ATTACHMENTS_RELEASE_ENABLED=enabled` is also required, and every direct upload repeats authentication and the health check at the server before reserving or reading the body. Each accepted file is then scanned again before storage. This workspace has no scanner URL/token and no deployed production scanner, so uploads remain unavailable here. Existing authenticated downloads and admin retention/removal controls do not depend on scanner uptime. Only JPEG, PNG and WebP uploads are supported; PDFs and other documents remain rejected.

Uploads require an authenticated owner of the account and, where supplied, its rental. The server reserves a rate-limited attempt before reading a bounded stream, checks the actual file signature against the declared PDF/JPEG/PNG/WebP type, hashes the bytes and requests a scanner verdict. The scanner contract requires a matching request nonce, digest and size; a complete clean verdict; no encryption, truncation or scan-limit failure; and a recent signature database. The server stores the scanned bytes only after that verdict, checks the stored hash, and publishes the message and file reference in one transaction. Downloads repeat the ownership and message checks, verify the stored hash and are served as private non-cacheable downloads. Repeated request keys do not publish a second message. A bounded sweep removes unpublished storage objects after a grace period.

The scanner interface is not itself a scanner. Before enabling the feature, deploy and maintain a private authenticated HTTPS scanning service, verify its identity, network restrictions, scanner configuration and current signatures, and qualify its exact verdict contract with real safe, EICAR, encrypted, malformed, decompression-limited and timeout fixtures. Establish an attachment-specific retention policy and its auditable deletion, case hold and erasure lifecycle for published messages and files; the verification-document retention policy does not automatically apply. Test cleanup and races, authenticated browser uploads and downloads, cross-account denial and recovery against an isolated deployment. Confirm capacity, monitoring, operational ownership and the data-processing basis. The local synthetic tests do not establish any of these production prerequisites.

`services/chat-scanner/` is a local prototype, not a deployed service. Its adapter accepts authenticated requests only on loopback, validates a SHA-256 digest, validates PDFs with `mutool` and images with `sharp`, then streams the exact bytes to a private ClamAV Unix socket. PDF temporary files require an owner-only tmpfs directory and are unlinked after validation; the deployment must destroy that isolated tmpfs after a crash. The supplied ClamAV configuration enables encrypted, broken-media and scan-limit alerts. The adapter rejects stale signature timestamps and a database reload during a scan. It requires a separately configured private TLS ingress, isolated non-root runtime, restricted outbound updates, current signatures, health checks and durable operational ownership. The unencrypted ClamAV socket must never be exposed on a network.

An isolated local run used the official `clamav/clamav` image digest `sha256:6d87c712e3391e13c1ba6e05dfb074d4b1ddb5a6834b23bb9da990d2a4ef042a`, updated its signature database, and tested a clean PDF, an encrypted PDF and EICAR. It also showed ClamAV alone returns `OK` for a malformed PDF, so the prototype rejects that file using a separate parser. A separate isolated engine test rejected one synthetic PDF whose compressed stream exceeded the configured limit; this test used a test-only clock because the image's bundled database was stale, and does not qualify every archive, nesting or decompression case. Malicious parser inputs, deployed TLS and sandbox isolation remain unqualified. The hard feature gate remains closed.

On 6 November 2026, another local engine run used that pinned image with networking disabled and the current scanner configuration. It rejected synthetic EICAR, encrypted-PDF and compressed-limit fixtures and accepted a clean PDF. Its bundled signatures were stale against the real clock, so the adapter correctly refuses to treat them as current; the engine fixture used a test-only clock. This is not qualification of a deployed scanner or its update process.

A later disposable local run updated its signature database separately before starting the network-isolated engine. With signatures current against the real clock, the real adapter accepted a synthetic clean PDF and rejected EICAR, encrypted and malformed PDFs; the engine rejected an oversized compressed-PDF fixture. The test used no customer data. This does not qualify production TLS, signature-update operations, parser isolation, retention or the complete live upload flow; the hard gate remains closed.

A later isolated test exercised the website upload handler through the real scanner and back to private storage using synthetic data. It rejected a PDF with data appended after its end marker, a forged second trailer, malformed content and a cross-account download. ClamAV returned `OK` for an appended EICAR test string, so this is a structural guard, not proof that ClamAV detects every polyglot or embedded threat. The conservative one-EOF policy also rejects legitimate incrementally updated or signed PDFs; a safe, usable document sanitisation strategy and broader adversarial qualification are still required before enabling uploads.

The prototype adapter image is pinned to a Node base digest and a locked `sharp` dependency. A local fixture ran that image and the real ClamAV engine as separate non-root containers with read-only root filesystems, no network, dropped capabilities, a group-restricted Unix socket and private tmpfs scratch. Clean-image, malformed-PDF and authentication tests passed; `SHUTDOWN`, `RELOAD` and `STATS` were denied on the scanner socket. The local adapter additionally rejects simple trailing data after JPEG, PNG and WebP endings; synthetic tests cover this boundary but do not establish protection against all polyglots or embedded threats. Because the socket cannot request reload, a production deployment needs a separately controlled, verified signature-update and rolling-engine-refresh process. This fixture is not a public TLS ingress, production deployment, penetration test or operational monitoring setup.

The scanner URL and bearer token are server-only. Never direct customer files to a public scanning service or enable uploads merely because those variables are present. A scanner outage hides new-upload controls but does not block already-published authenticated downloads or retention actions.

Upload retries are bound to the file's digest, size, type and displayed name. A retry with a different file cannot report the original upload as successful. Published-file replays are rate-limited before the body is read. The client also identifies pending retries by the actual bytes rather than filename and timestamps. An isolated local Convex test checks concurrent publication, byte-exact download and cross-account denial using a simulated scanner and a test-only readiness override; it does not qualify the production scanner or deployment.

An isolated end-to-end run with a current ClamAV database, real scanner adapter and local Convex storage found that ClamAV returned clean for harmless EICAR signatures embedded in PNG, JPEG and WebP metadata. The adapter now conservatively rejects unsupported metadata-bearing chunks or segments before scanning; basic clean fixtures and progressive JPEG pass. This also rejects many legitimate files containing metadata, including common camera photos, and does not prove arbitrary image content or PDF threats are safe. The test uses a test-only loopback bridge and readiness override. Safe sanitisation, compatibility, production isolation, delivery and retention still require qualification before enabling attachments.

After an image upload fails, the local chat offers an explicit cleaned-copy retry. The browser converts the selected image to PNG, removes metadata and sends the copy only after the user clicks the option; the original remains on the device. The UI warns that colours may change. Rendering, orientation and colour fidelity need testing on real mobile browsers, and a cleaned copy is not a substitute for preserving an original evidentiary file. No PDF is altered by this option.

The local prototype also provides admin-only manual retention holds and a reasoned, confirmed removal action. An open or unresolved case for the rental (or, for general support files, the account) prevents removal. For support files the check includes permanently linked bookings and legacy bookings with the account's normalised email, including old case rows without an account ID; histories beyond the bounded review limit fail closed. Legacy records with non-normalised or changed email need separate review. The removal checks the message and stored-object binding, deletes the bytes, replaces the chat entry with an attachment-removed marker and retains a minimal action audit and retry tombstone. Published rental attachments are deleted 90 days after a rental is returned or cancelled unless a damage case has ever been opened for that rental. A case opening creates a permanent archive record for that rental conversation; its messages and attachments remain linked to the case after it closes. General support chats remain separate: they auto-close after 90 idle days, reopen when someone writes again, and their attachments expire 90 days after closure. An open case temporarily protects account-level support files. Missing closure dates, inconsistent file/message bindings, manual holds and case-history errors fail closed and are shown for review. Deletion audit rows are retained for 90 days after attachment deletion. The permanent case archive needs a documented purpose, lawful basis and rights-handling process before production use. Retrying an old upload request cannot restore removed content.

Manual hold changes and deletion are fenced by the exact hold revision the administrator confirmed. A hold added and later released still advances the revision, so an older confirmation cannot release or delete against the newer state. An open-case check remains authoritative at removal time; this revision does not replace it.

Upload filenames are sent in a request header rather than the URL, so normal URL access logs do not expose them. Header logging must also be disabled or redacted for this endpoint in every proxy and observability layer.

The local scanner now checks that its harmless EICAR test signature is detected during every file scan, not just when a readiness probe is called. It rejects the upload if this test fails or its signature version changes during the scan. This adds an extra engine scan per upload and still cannot prove detection of every threat; capacity and latency need measuring before rollout. The attachment gate remains closed.

The upload client uses the same strict HTTPS `/scan` endpoint, minimum token length and ClamAV version format as the readiness check. Misconfigured paths, query strings, credentials and malformed engine or signature versions fail closed before an attachment can be published.

WebP still-image validation rejects duplicate or mixed image chunks, misplaced alpha data and unsupported extended flags. A synthetic duplicate-image fixture was accepted by the decoder and previously passed the structural check, demonstrating that successful decoding alone does not establish that all container content is safe. The gate remains closed pending broader adversarial testing.

PNG validation also checks that the complete concatenated image-data stream is consumed and limits decompressed output to a conservative bound derived from image dimensions. A synthetic valid-looking PNG carried extra bytes after its compressed image data and was accepted by the decoder and previous structural check. This additional check rejects that case; it is not a guarantee against all image threats.

Downloads recheck session, ownership and file-to-message binding after reading and hashing the stored bytes. Revocation or removal during that read therefore prevents delivery; this cannot retract bytes already delivered or eliminate the small interval after the final check. The production attachment gate remains closed.

A disposable local Convex backend test additionally verifies that an expired session and a removed message binding deny an existing download, and that restoring the exact binding restores the owner's access. It uses a synthetic scanner and data, and does not demonstrate a revocation occurring during the actual storage read; that race is exercised by the separate handler fixture.
