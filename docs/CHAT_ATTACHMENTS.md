# Chat attachments

## Current status — 11 November 2026

Chat attachments remain disabled. The renter and admin upload controls require `CHAT_ATTACHMENTS_RELEASE_ENABLED=enabled`, a configured private HTTPS scanner and a successful authenticated health check. This workspace has no production scanner URL/token or deployed scanner. Existing authenticated downloads and admin retention/removal controls do not depend on scanner uptime.

Only JPEG, PNG and WebP images up to 10 MiB are supported. All PDFs and other documents are rejected before a clean scanner verdict can be issued. Image uploads require an authenticated account owner and, when linked to a rental, the booking owner. The server bounds and rate-limits the upload, validates image structure, hashes it, checks the private scanner's nonce/digest/size/current-signature verdict, stores the exact scanned bytes, checks the stored hash and publishes the message atomically. Preview and download remain authenticated, ownership-checked and non-cacheable.

On this date, an isolated run used the official `clamav/clamav` image pinned to `sha256:2d901d81cbd1ed6556edfde8e20391bf81a13365d8f3ad9460d1c0340470ad89`, downloaded and validated current signatures, and exercised the actual local HTTP upload handler with synthetic data. Clean PNG upload/download, cross-account denial, EICAR rejection, malformed content rejection and clean/encrypted PDF rejection passed. ClamAV itself returned `OK` for the encrypted PDF fixture, which is why the application rejects every PDF before relying on an engine verdict. This local test does not qualify production ingress, recurring signature updates, monitoring, all mobile images, retention/legal basis or production deployment.

## Security and deployment requirements

Uploads require an authenticated owner of the account and, where supplied, its rental. The server reserves a rate-limited attempt before reading a bounded stream, checks the actual file signature against JPEG/PNG/WebP, hashes the bytes and requests a scanner verdict. The scanner contract requires a matching request nonce, digest and size; a complete clean verdict; no truncation or scan-limit failure; and a recent signature database. The server stores the scanned bytes only after that verdict, checks the stored hash, and publishes the message and file reference in one transaction. Image messages load a lazy inline preview through the same authenticated, ownership-checked, hash-verified no-store route with `nosniff` and a sandbox policy. Download remains a separate private, non-cacheable action. Repeated request keys do not publish a second message. A bounded sweep removes unpublished storage objects after a grace period.

The scanner interface is not itself a scanner. Before enabling the feature, deploy and maintain a private authenticated HTTPS scanning service, verify its identity, network restrictions, scanner configuration and current signatures, and qualify its exact verdict contract with real safe, EICAR, encrypted, malformed, decompression-limited and timeout fixtures. Establish an attachment-specific retention policy and its auditable deletion, case hold and erasure lifecycle for published messages and files; the verification-document retention policy does not automatically apply. Test cleanup and races, authenticated browser uploads and downloads, cross-account denial and recovery against an isolated deployment. Confirm capacity, monitoring, operational ownership and the data-processing basis. The local synthetic tests do not establish any of these production prerequisites.

`services/chat-scanner/` is a local prototype, not a deployed service. Direct local runs bind to loopback; the container listens on all interfaces for a private ingress. The adapter validates a SHA-256 digest and image structure, then streams accepted image bytes to a private ClamAV Unix socket. It currently rejects every PDF before scanning; older PDF-oriented notes below are superseded. The supplied ClamAV configuration enables encrypted, broken-media and scan-limit alerts, but the local real-engine run showed that an encrypted PDF may still receive `stream: OK`; application policy must continue to reject PDFs unless a separately qualified parser/sanitizer path is built. The adapter rejects stale signature timestamps and a database reload during a scan. Production requires a private TLS ingress, isolated non-root runtime, restricted outbound updates, current signatures, monitoring and operational ownership. The unencrypted ClamAV socket must never be exposed on a network.

Earlier local experiments in the repository explored multiple PDF scanning/parser configurations and produced mixed engine results. Those historical experiments are not the current file policy: all PDFs are now rejected, and none of the earlier results authorize PDF uploads.

The prototype adapter image is pinned to a Node base digest and a locked `sharp` dependency. A local fixture ran that image and the real ClamAV engine as separate non-root containers with read-only root filesystems, no network, dropped capabilities, a group-restricted Unix socket and private tmpfs scratch. Clean-image, malformed-PDF and authentication tests passed; `SHUTDOWN`, `RELOAD` and `STATS` were denied on the scanner socket. The local adapter additionally rejects simple trailing data after JPEG, PNG and WebP endings; synthetic tests cover this boundary but do not establish protection against all polyglots or embedded threats. Because the socket cannot request reload, a production deployment needs a separately controlled, verified signature-update and rolling-engine-refresh process. This fixture is not a public TLS ingress, production deployment, penetration test or operational monitoring setup.

The scanner URL and bearer token are server-only. Never direct customer files to a public scanning service or enable uploads merely because those variables are present. A scanner outage hides new-upload controls but does not block already-published authenticated downloads or retention actions.

Upload retries are bound to the file's digest, size, type and displayed name. A retry with a different file cannot report the original upload as successful. Published-file replays are rate-limited before the body is read. The client also identifies pending retries by the actual bytes rather than filename and timestamps. An isolated local Convex test checks concurrent publication, byte-exact download and cross-account denial using a simulated scanner and a test-only readiness override; it does not qualify the production scanner or deployment.

An isolated end-to-end run with a current ClamAV database, real scanner adapter and local Convex storage found that ClamAV returned clean for harmless EICAR signatures embedded in PNG, JPEG and WebP metadata. The adapter now conservatively rejects unsupported metadata-bearing chunks or segments before scanning; basic clean fixtures and progressive JPEG pass. This also rejects many legitimate files containing metadata, including common camera photos, and does not prove arbitrary image content or PDF threats are safe. The test uses a test-only loopback bridge and readiness override. Safe sanitisation, compatibility, production isolation, delivery and retention still require qualification before enabling attachments.

After an image upload fails, the local chat offers an explicit cleaned-copy retry. The browser converts the selected image to PNG, removes metadata and sends the copy only after the user clicks the option; the original remains on the device. The UI warns that colours may change. Rendering, orientation and colour fidelity need testing on real mobile browsers, and a cleaned copy is not a substitute for preserving an original evidentiary file. No PDF is altered by this option.

The local prototype also provides admin-only manual retention holds and a reasoned, confirmed file-removal action. An open rental case protects attachments on that booking's rental conversation only; it does not hold files from unrelated support chats. A case opening permanently archives that rental conversation, its messages and its attachments. Archived rental attachments have no automatic expiry and ordinary admin hold/removal controls are unavailable for them. The case row and archive link are written in one mutation; the deletion job reads that booking's case/archive state in its own transaction before deleting bytes, so a concurrent case open conflicts and retries instead of silently deleting newly archived evidence. If deletion has already committed before a case is opened, the bytes cannot be restored. General support chats remain separate: they auto-close after 90 idle days, reopen when someone writes again, and their attachments expire 90 days after closure. Missing closure dates, inconsistent file/message bindings, manual holds and case-history errors fail closed and are shown for review. Deletion audit rows are retained for 90 days after attachment deletion. The permanent case archive needs a documented purpose, lawful basis and rights-handling process before production use. Retrying an old upload request cannot restore removed content.

Manual hold changes and deletion are fenced by the exact hold revision the administrator confirmed. A hold added and later released still advances the revision, so an older confirmation cannot release or delete against the newer state. A permanent case-archive check remains authoritative at removal time; this revision does not replace it.

Upload filenames are sent in a request header rather than the URL, so normal URL access logs do not expose them. Header logging must also be disabled or redacted for this endpoint in every proxy and observability layer.

The local scanner now checks that its harmless EICAR test signature is detected during every file scan, not just when a readiness probe is called. It rejects the upload if this test fails or its signature version changes during the scan. This adds an extra engine scan per upload and still cannot prove detection of every threat; capacity and latency need measuring before rollout. The attachment gate remains closed.

The upload client uses the same strict HTTPS `/scan` endpoint, minimum token length and ClamAV version format as the readiness check. Misconfigured paths, query strings, credentials and malformed engine or signature versions fail closed before an attachment can be published.

WebP still-image validation rejects duplicate or mixed image chunks, misplaced alpha data and unsupported extended flags. A synthetic duplicate-image fixture was accepted by the decoder and previously passed the structural check, demonstrating that successful decoding alone does not establish that all container content is safe. The gate remains closed pending broader adversarial testing.

PNG validation also checks that the complete concatenated image-data stream is consumed and limits decompressed output to a conservative bound derived from image dimensions. A synthetic valid-looking PNG carried extra bytes after its compressed image data and was accepted by the decoder and previous structural check. This additional check rejects that case; it is not a guarantee against all image threats.

Downloads recheck session, ownership and file-to-message binding after reading and hashing the stored bytes. Revocation or removal during that read therefore prevents delivery; this cannot retract bytes already delivered or eliminate the small interval after the final check. The production attachment gate remains closed.

A disposable local Convex backend test additionally verifies that an expired session and a removed message binding deny an existing download, and that restoring the exact binding restores the owner's access. It uses a synthetic scanner and data, and does not demonstrate a revocation occurring during the actual storage read; that race is exercised by the separate handler fixture.
