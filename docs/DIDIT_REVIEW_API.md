# Didit review decision flow

Only a provider session whose current status is `In Review` appears as a manual-review case. Ordinary `Approved` results are authoritative: the site records the approval and its 90-day reuse window without running separate identity/address approval rules. `adminVerificationLink` opens the bound Didit case and returns only sanitized provider warnings; `refreshProgress` re-reads Didit's current decision and reconciles it with the rental.

The admin review card can approve, decline, or request resubmission. Before changing Didit, `adminReview` authenticates the operator, checks the rental/session binding and verification deadline, reserves a per-rental review claim, and fetches the current provider decision. It requires `In Review`; for resubmission it asks Didit for the exact retry steps. The action updates Didit with an idempotency key and `send_email: false`, then retrieves the session again and updates the website only if Didit confirms the requested status. An unconfirmed provider status cannot create a website approval; if the update succeeds but the readback fails, refresh the case before taking another action.

Before dispatch, the website records an uncertain-outcome fence and a random marker appended to the provider review comment. If the response is lost, refresh checks at most the 50 newest entries in Didit's session review audit. Only a matching marker, API-key actor, target status and plausible timestamp, combined with the same bound session and a reconciled website status, release the fence. Missing, unavailable, old, or mismatched audit evidence leaves the case locked for investigation; a current status alone is not proof of which request caused it. Older claims without a marker also remain locked. This path performs no provider write. Didit's 24-hour idempotency replay requires the same credential and exact request; the website does not currently persist enough information to replay safely.

References: https://docs.didit.me/sessions-api/update-status, https://docs.didit.me/management-api/sessions/list-reviews, https://docs.didit.me/integration/api-errors.

Didit documents the update endpoint, its `write:sessions` permission, optional email previews, and idempotency-key behavior at https://docs.didit.me/sessions-api/update-status. The API can change a final decision, so the website intentionally refuses to act unless the latest provider status is still `In Review`; its pre-update read, idempotency key, and post-update read protect the decision from stale or conflicting actions. The operator's reason is recorded in Didit's review trail. The website is the sole renter-email sender: it sends the appropriate review, resubmission, or decline update, and after an already-confirmed rental is approved it sends the canonical confirmation email with invoice and pickup details. Paid bookings awaiting initial confirmation receive that approval email only after the normal payment, stock, and verification gates complete. The site also performs its normal archive, rental-manager and chat transitions after it confirms the provider result.

For Didit webhook signing-key rotation, keep the old destination secret in `DIDIT_WEBHOOK_SECRET_PREVIOUS` for the documented 24-hour overlap while `DIDIT_WEBHOOK_SECRET` contains the new key. The receiver validates both regular and `-Previous` full-payload signature headers against the configured keys; remove the previous secret after Didit's overlap expires. It does not fall back to the deprecated envelope-only `X-Signature-Simple` header.

The account sidebar's manual-review queue is indexed independently from the latest-rentals projection, shows up to 20 open cases, and indicates when more remain. Older unlinked bookings are discoverable only when their stored email exactly matches the account's normalized email; records with changed or non-normalized addresses require separate reconciliation.
