# Didit review decision boundary

Didit's documented v3 session update endpoint now supports `Approved`, `Declined` and `Resubmitted` through `PATCH /v3/session/{sessionId}/update-status/`. It requires `write:sessions`; `send_email` defaults to false. A successful response contains the session ID, not the updated decision, and Didit instructs callers to retrieve the session again. See https://docs.didit.me/sessions-api/update-status.

This repository does not yet issue those writes. The current manual-review panel directs an administrator to the Didit console and then refreshes the website's status. This is deliberate: the API documentation says an approval and a decline can overturn each other, while the documented request provides no conditional expected-status or version field. A pre-read alone cannot prevent an intervening provider decision being overwritten. Local event fencing protects the website's state, not the provider's. A timeout after a write is also an unknown outcome, not proof that nothing changed; resubmission may clear checks and must not be blindly retried.

Didit's optional email-preview receipt rejects an update if the session status or other previewed details change, but the documentation requires `send_email: true` with that receipt. It is not a documented no-email compare-and-set, and adopting it would also send the previewed provider email. It needs an explicitly designed customer-notification and concurrent-review workflow before use. The website can locally reconcile an already matching provider `Declined` or `Resubmitted` result with event fencing, without changing Didit; an unmatched requested decision is still directed to the provider console. This does not solve provider-side races or the legacy administrator authentication gap.

Before enabling provider-write controls, establish a provider-supported concurrency policy, an auditable confirmed operation and recovery of ambiguous outcomes. Test approval, decline, resubmission, stale decisions, lost responses, signed webhooks, owner changes, cancellation/refund effects and duplicate notifications using an isolated Didit sandbox application and synthetic identities. Do not send a notification during fixture tests. See https://docs.didit.me/integration/sandbox-testing. The account sidebar uses a separate indexed queue independent of the latest-100-rental projection, shows up to 20 open review cases, and indicates when more remain. Older unlinked bookings are discoverable only when their stored email exactly matches the account's normalized email; records with changed or non-normalized addresses require separate reconciliation.
